A cache replacement policy is a prediction problem wearing the costume of a data structure. The structure part is easy and the prediction part is the whole difficulty, which is why the literature is large and the practical gap between policies is usually small.

Consider the simplest possible framing. A cache holds N objects. A request arrives for an object; if it is present, that is a hit and costs nothing. If it is absent, that is a miss, the object must be fetched, and something already resident must be discarded to make room. The policy is the rule that chooses what to discard. Belady's algorithm chooses the object whose next request is furthest in the future, which is provably optimal and unimplementable, since it requires knowledge of requests that have not happened yet. Every real policy is therefore an approximation of Belady using only the past.

Least Recently Used approximates it by assuming recency predicts reuse. This assumption is correct often enough that LRU has been the default for decades, and wrong in a specific way that matters: it has no notion of frequency. An object requested once and never again is treated identically to an object requested a thousand times, provided both were touched at the same moment. A scan through a large working set therefore evicts everything valuable in favour of everything worthless, and the hit rate collapses to zero. This is not a pathological corner case. It is what a sequential pass over data larger than the cache does, every time.

Frequency-aware policies correct for this by tracking how often an object has been used, not merely when. The naive form, Least Frequently Used, has the opposite failure: an object that was popular long ago accumulates a count that a currently popular object cannot overcome, and the cache fills with stale winners. Practical designs therefore combine the two signals and add a mechanism for forgetting. Window TinyLFU maintains a frequency sketch with periodic halving of all counts, so history decays rather than accumulating forever. S3-FIFO takes a different route: it admits new objects to a small probationary queue, promotes only those requested again while there, and keeps a ghost queue of recently evicted keys so that a second miss on the same key can be distinguished from a first.

The reason these designs win is not that they predict better in general. It is that they fail differently. The workload determines which failure is cheaper, and the only way to know is to replay the actual request trace against each candidate. Reasoning from the mechanism will tell you which policy should win; it will not tell you by how much, and it will not warn you when a tuning constant chosen by analogy is wrong for the size of cache you actually have.
